# Personal Depth Analyzer

> 个人技术薄弱点深度审查器 — 穿透表象，直达本质。

通过五层分析法从错误表象逐层追溯到认知体系根因，生成包含可视化图表的 HTML 交互式报告。

---

## 它能做什么

与普通的"代码审查"或"错误纠正"不同，本工具的核心差异在于**深度**：

| 普通工具 | 本工具 |
|---------|--------|
| "你的 DP 写错了" | "你没有建立重叠子问题的识别直觉" |
| "建议多练习" | "完成 5 道一维 DP，每道强制：递归 → 递归树 → 发现重叠 → 改写迭代" |
| 停留在技术层 | 从表象 → 模式 → 技术 → 认知 → 体系，五层逐层下钻 |
| 通用建议 | 根据你的学习阶段、时间预算、目标定制方案 |

---

## 执行思路

整个分析流程分为 5 个阶段：

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  Phase 1    │     │  Phase 2    │     │  Phase 3    │     │  Phase 4    │     │  Phase 5    │
│  配置确认    │ ──▶ │  五层分析    │ ──▶ │  根因追溯    │ ──▶ │  生成报告    │ ──▶ │  交互迭代    │
│             │     │             │     │             │     │             │     │             │
│ · 分析深度  │     │ L1 表象层   │     │ · 直接原因  │     │ · 执行摘要  │     │ · 深入某个点 │
│ · 领域权重  │     │ L2 模式层   │     │ · 认知原因  │     │ · 可视图表  │     │ · 替换方案   │
│ · 输出格式  │     │ L3 技术层   │     │ · 根源追溯  │     │ · 薄弱剖析  │     │ · 补充分析   │
│ · 学习风格  │     │ L4 思想层   │     │ · 泛化风险  │     │ · 行动清单  │     │ · 制定周计划 │
│ · 时间预算  │     │ L5 体系层   │     │ · 根本方案  │     │ · 学习路径  │     │ · 调整强度   │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
```

### 五层分析法详解

每一层都必须有**明确的证据支撑**，不允许跳跃或猜测：

| 层次 | 关注点 | 核心问题 |
|------|--------|---------|
| **L1 表象层** | 错误现象 | 具体发生了什么？在什么场景下触发？ |
| **L2 模式层** | 重复规律 | 是偶发还是重复？不同场景下有什么共同特征？ |
| **L3 技术层** | 技能缺失 | 缺少哪个知识点？是理解偏差还是完全不知道？ |
| **L4 思想层** | 认知缺陷 | 反映了什么思维模式缺陷？缺乏系统性还是抽象能力？ |
| **L5 体系层** | 知识结构 | 在整个知识体系中处于什么位置？修复需要哪些前置知识？ |

## 使用方法

### 1. 准备输入材料

提供以下一种或多种材料（材料越充分，分析越深入）：

- **错误代码** — 失败的实现 + 正确的实现对比
- **Bug 报告** — 错误消息、堆栈跟踪、修复过程
- **问题日志** — 你当时的思考过程、尝试过的方案
- **参考资源** — 标准答案、最佳实践（可选）

### 2. 选择分析配置

**分析深度：**

| 级别 | 说明 | 适合场景 |
|------|------|---------|
| 快速扫描 | 仅分析到 L2（表象+模式） | 时间有限，快速摸底 |
| 标准分析 | 分析到 L3（+技术层） | 常规学习复盘 |
| 深度诊断 | 全部五层 | 系统性提升 |

**快速模板（开箱即用）：**

| 模板 | 深度 | 重点领域 | 风格 | 时间 |
|------|------|---------|------|------|
| 面试冲刺 | 标准 | 算法权重 5 | 实践导向 | 1-2h/天 |
| 工作提升 | 深度 | 框架权重 5 | 混合型 | 30min/天 |
| 入门学习 | 快速 | 语言基础权重 5 | 理论导向 | 30min/天 |

### 3. 获取报告

分析完成后，你会收到一份 **HTML 交互式报告**，包含：

```
📊 执行摘要          — 一段话概括核心发现
🎯 数据概览          — 严重程度饼状图 + 领域分布图
💪 知识体系          — 树形图展示已掌握的知识
⚠️ 薄弱剖析          — 每个薄弱点的五层完整分析
🧠 认知诊断          — 优势思维 vs 待改进思维
🚀 行动清单          — P0/P1/P2 分级的具体行动项
📈 学习路径          — 分阶段学习路线
ℹ️ 分析局限          — 本次分析的边界说明
```

### 4. 迭代优化

拿到报告后，你可以：

- "这个分析点我想深入了解" → 更深层次的根因追溯
- "这个建议不适合我" → 重新生成替代方案
- "帮我制定一个 4 周计划" → 行动项分解为周计划
- "给我一个更激进的方案" → 调整强度和节奏

## 分析示例

**输入（来自真实项目的问题集合）：**

```
Bug #1: 用户反馈订单状态不更新
  - 后端日志: "订单已支付，但回调通知发送失败"
  - 重试 3 次后放弃，状态停留在"待支付"
  - 用户刷新页面才看到正确状态

Bug #2: 后台管理员无法手动关闭订单
  - 接口返回 403，但前端没有区分"无权限"和"状态不允许"
  - 管理员看到的是空白错误提示

Bug #3: 优惠券核销后，用户端仍显示"可用"
  - 库存服务通知已发送，但用户服务接收超时
  - 用户下单时看到优惠券可用，实际无法使用

Bug #4: 活动开始前，用户看到了活动入口
  - Redis 缓存的"活动配置"TTL 到了
  - 直接返回了空/默认值，前端判断"有活动"而非"无活动"

Bug #5: 支付成功页的倒计时不准确
  - 用了本地 Date.now()，用户修改手机时间就乱跳
  - 应该用服务端返回的时间戳
```

---

**输出（五层深度分析）—— 薄弱点：缺乏分布式系统的"最终一致性"思维**

---

**L1 表象层：多个模块各自独立正常，但组合起来出现数据不一致**

| Bug | 模块 | 现象 |
|-----|------|------|
| #1 | 订单服务 ↔ 通知服务 | 订单状态变了，通知没发出去 |
| #3 | 用户服务 ↔ 库存服务 | 优惠券核销了，用户端没感知 |
| #4 | 配置服务 ↔ 前端 | 缓存过期，前端拿到错误默认值 |

---

**L2 模式层：问题总发生在"跨服务边界"的地方**

- 这 5 个 bug 中，有 4 个涉及**两个或以上服务的通信**
- 单独测试每个服务都是正常的（单元测试全绿）
- 但在**集成场景下**，数据流经过多个服务时，状态开始分裂
- 共同特征：**写操作成功 ≠ 下游消费者成功**

---

**L3 技术层：缺失"可靠消息传递"的技术方案**

具体知识点缺失：

1. **消息队列的确认机制**（Bug #1）
   - 发送消息后没有等待 broker ACK 就返回成功
   - 应该：持久化 → 发送 → 等待 ACK → 更新本地状态

2. **幂等性设计**（Bug #3）
   - 消息可能被重复消费，但服务没有做幂等校验
   - 应该：每条消息带唯一 ID，消费者先查"是否已处理"

3. **缓存穿透的防御性编程**（Bug #4）
   - 缓存 miss 时直接用默认值，缺少"无效值"的区分
   - 应该：null ≠ 空数组 ≠ 正确值，三种情况分别处理

4. **前端不做服务端时间同步**（Bug #5）
   - 直接用 `new Date()` 或 `Date.now()`
   - 应该：登录时同步服务端时间戳，后续用相对时间

---

**L4 思想层：持有"同步即一致"的隐含假设**

这个 bug 集合的根因认知是：**把"调用返回成功"等同于"整个链路处理完成"**。

思维链条：

```
我调用了库存服务 → 库存服务返回"核销成功" → 我认为用户看到的也是"已核销"
```

但实际的数据流是：

```
库存服务 → 消息队列 → 用户服务（异步） → 前端缓存 → 用户看到
```

用户看到的"已核销"比库存服务的"核销成功"**晚了 1-3 秒**。

这反映了一种**"顺序思维"**：习惯于单线程、单函数内的线性逻辑（调用 → 等待 → 返回 → 完成），而缺乏**"并发链路"的心智模型**——数据从 A 到 B 到 C 到 D，每一跳都可能失败、延迟、乱序。

---

**L5 体系层：前端开发者向服务端领域的认知盲区**

这个薄弱点位于"**前后端边界认知**"区域，影响范围：

```
影响领域：
├── 订单模块（消息通知）
├── 营销模块（优惠券、活动）
├── 配置模块（开关、灰度）
└── 支付模块（回调、对账）

前置知识缺失：
├── 消息队列（Kafka/RabbitMQ）
├── 分布式事务（Saga/2PC/TCC）
├── CAP 定理与最终一致性
└── 前端时间同步方案
```

这不是"某个 API 不会调用"的问题，而是**整个分布式协作范式的认知盲区**。

---

**解决方案（具体可执行）：**

| 阶段 | 行动 | 验证方式 |
|------|------|---------|
| 立即行动 | 阅读《分布式系统设计：可靠消息传递》章节，做笔记 | 能用自己的话解释"at least once" vs "exactly once" |
| 本周内 | 在测试环境复现 Bug #1，给消息队列加监控 | 能在日志中定位消息的发送和消费时间差 |
| 两周内 | 完成一个"订单 → 消息 → 库存 → 用户"的全链路测试 Demo | 给定一个失败场景，能独立定位到具体是哪个环节超时 |
| 一个月 | 在实际项目中引入幂等设计，对所有写接口加唯一请求 ID | code review 时能说出每条消息的幂等策略 |
